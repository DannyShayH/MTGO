These definitions explain how each metric is calculated, where its data comes from and how to interpret it. The [shared glossary](/MTGO/architecture/glossary/) defines the team's product and workflow vocabulary, including preferred terms and synonyms to avoid.

## Sources and refresh

Numbers come from [Project #2](https://github.com/users/DannyShayH/projects/2), refreshed during delivery and daily at 05:00 UTC. The collection time is shown on every metrics page. A manual refresh is available in GitHub Actions.

Local builds without board access show a **Sample data** banner. An expired or rejected token fails collection so it cannot publish sample numbers by accident. The [published metrics JSON](/MTGO/flow-metrics.json) contains the same numbers used by the charts and tables.

Charts use Copenhagen calendar dates. Weeks run Monday to Sunday. Empty throughput weeks have no bar; weeks without usable cycle times have a gap in the line.

## Work item

The agreed policy is an issue on the project board with no sub-issues that is not a Feature. Parent issues and Features awaiting sub-issues are excluded; their work items are counted instead.

The mandatory title prefix `Feature: ` identifies a Feature independently of child count. An empty Feature and a Feature with children contribute nothing to WIP, Ready, throughput, cycle time, elapsed time, age, blocked work, cumulative flow or breach calculations. An ordinary structural parent remains excluded without becoming a Feature. Eligible standalone and child work items keep their existing board membership and count once. See [ADR-0016](/MTGO/architecture/decisions/0016-feature-identity-and-completion-evidence/).

**Historical correction, 12 November 2026 (#58):** Every build recalculates the available work-item history from the collected dataset with this exclusion applied before replaying status events. Previously counted empty Features are removed from historical counts as well as current values. All views and the published JSON use the same dataset and observation time. Past written flow-review observations remain unchanged; the [week 46 correction note](/MTGO/flow-reviews/2026-w46/#counting-correction-12-november-2026) explains the change for the next review.

**Renamed Features (#62):** The collector reads every page of retained title history and keeps recognition attached to the issue's stable GitHub identity. A previously recognized Feature therefore stays out of current and historical work-item metrics when its current title loses the mandatory prefix. Its Feature observation and Features view show a linked naming problem; collection never edits the title or board. Repeated source entries are deduplicated by stable identity. An incomplete title-history connection fails collection before publication, because absence of a retained event has not been established.

**Evidence limits:** Recognition can use only title history retained and returned by GitHub. Deleted or unavailable source evidence is not reconstructed or guessed. Archived Features and Feature children outside the board are retrieved only as Feature evidence (#65); missing dates are never invented.

[Feature #42 discovery](/MTGO/flow-metrics/feature-discovery/) records the agreed recognition and completion rules, source evidence and acceptance examples for the remaining Feature reporting work.

## Feature age and required work

The [Features view](/MTGO/flow-metrics/features/) lists current open and completed issues recognized by the mandatory `Feature: ` title prefix or retained evidence of that prefix in their title history. A recognized Feature whose current title lacks the prefix has a linked naming problem; the collector does not repair it. Every native direct child is required, including discovery. Counts say **delivered required work items out of required work items**, never a percentage of business capability. An empty Feature says “No work items yet” and is not completed. Blocking dependencies do not create membership.

Feature age is the Copenhagen calendar days between the earliest valid child project Start date and the shared observation date. Same-day age is zero in the published JSON and displays as “< 1 day”. Discussion and dates on the parent do not supply the Feature start. A Backlog or Ready child without a Start date is normally not started. A started or delivered child with a missing, invalid or future Start date makes Feature timing unavailable, even when a sibling has a usable date. Linked explanations identify the affected child. Closing never-started work as not planned does not establish a start or invalidate a sibling’s valid timing. Child details show current status, Start and close dates, plus work-item age or completed cycle time when applicable.

**Current scope (#60):** Direct-child connections are fully paginated before publication. Children are matched by issue URL to the current board dataset; a child outside that population has linked unavailable board evidence and cannot supply guessed timing. Nested parents are flagged as unsupported rather than recursively counted. If required child delivery evidence is unavailable or unsupported, the delivered count is also unavailable, never zero by default. A closed child with no close reason is not counted as delivered, but its delivery outcome is unknown rather than confirmed as not planned. Its linked data problem makes the aggregate delivered count unavailable; usable Start dates still support Feature age. Features and child evidence never expand the existing work-item population. Pages and published JSON share one source and observation time; representative sample Features remain behind the sample banner. The sample includes illustrative relationships, not a claim about the live board.

Removed scope is recorded on the parent with one readable line for each exception: `Scope decision: #123 — removed — reason: duplicate work`. Only a valid record naming a linked child and giving a reason removes that child from the current required-work denominator and required finish. Removed children remain visible separately, and their valid Start dates still contribute to the Feature's original start. Malformed, duplicate or unknown-child records remain required and appear as data problems. A conflicting or incomplete second record for the same child invalidates its removal, regardless of record order. Removed work with neither a Start date nor status evidence is unavailable timing, rather than proof that it never started. A child closed as not planned is never delivered work. Children that left the Feature are covered by [moved and late-linked work](#moved-and-late-linked-work); missing facts stay visible and incomplete connection retrieval fails collection rather than publishing partial results.

**Archived and off-board evidence (#65):** The collector reads Project #2 items in both archived states. An archived Feature stays in the Features view, marked “(archived)”, with the same start, finish and lead time it had before archival. Archived children of a Feature are kept as its evidence. Other archived items are dropped, so archival still removes a work item from the work-item charts exactly as before. A direct child that is neither on the board nor archived on it is read by its issue identity, together with all of its project items, archived ones included, to find its Project #2 Status and Start date. This Feature evidence is a separate population: it never adds work items, WIP, throughput, cycle times or work-item data problems. A stable issue identity counts an issue once, and the normal board copy wins over an evidence copy.

The two kinds of failure are kept apart. When GitHub answers that a child issue cannot be found (`NOT_FOUND` on that node, and no other error), the child stays in the Feature with “Child board evidence is not available”, and when the child has no Project #2 item it is shown with “Child is not on Project #2; its Status and Start date are not available”. A child that has lost its Start date is identified with the usual missing-date problem. In each case Feature timing is unavailable rather than shortened. Authentication, transport, GraphQL errors and incomplete pagination of the items, child, timeline or project-item connections stop the refresh before publication. **Evidence limit:** current direct children are followed through the Feature's child list, and former children through its retained sub-issue removal events (#66). An issue deleted on GitHub cannot be recovered. GitHub gives the same `NOT_FOUND` answer for a child in a repository the board token cannot read, so a missing token permission on such a child shows as “Child board evidence is not available” rather than stopping the refresh. A Feature showing that problem for a child that still exists points to the token's repository access.

## Moved and late-linked work

Membership is reconstructed from the Feature's native `SubIssueAddedEvent` and `SubIssueRemovedEvent` timeline history, read across every timeline page, without board snapshots, a metrics-data branch or writes to the board (#66). A **former child** is one whose latest retained event is a removal and that is not a current child; a child reattached later is current, required work again. Each former child is read by the stable issue identity the event retains, through the same path as off-board and archived children, so its preserved project Start date counts even when it is archived or no longer on the board.

- **Moved** work was added to another parent when it left, shown with a link to that parent. The destination is the first parent that recorded adding the child from the removal onwards (within a minute, since GitHub records a parent change as two events), so a later second move or unlink does not rewrite it. When no parent in the dataset recorded that addition, the child's current parent is shown instead. **Unlinked** work has no parent. Both appear with removed scope, outside the required-work count and finish, and give their reason through the same `Scope decision: #123 — removed — reason: …` record on the former Feature. A former child without that record keeps its timing contribution and shows a linked problem asking for the reason.
- A former child's actual Start date keeps supplying the former Feature's original start, so moving or unlinking the earliest work does not restart the Feature. Work that started only after it left (Start date later than the Copenhagen date of the removal) is marked “started after leaving” and supplies no start.
- A child's actual Start date also counts in the receiving Feature, even when it predates the attachment or the parent's creation. A child that starts 16 November, is attached on 19 November and is delivered on 20 November gives four days once completion is accepted. Attachment, creation and In Progress events never supply a start.
- The child remains one work item: it is counted once in throughput, cycle time and WIP even when it contributes evidence to two Features.

In the published JSON, a child's `scope` is `Required`, `Removed`, `Moved` or `Unlinked`; former children add `leftAt` (the removal timestamp) and `movedTo` (the parent it moved to, or `null`), and `removedChildren` lists every child that is not required.

**Missing history:** a removal event whose child GitHub can no longer show, a former child GitHub answers as not found, or a former child that started but lost its Start date makes the Feature's timing unavailable, with a linked explanation; no sibling date replaces it. A former child with neither a Start date nor status evidence is unavailable too, because its earlier start cannot be ruled out. Removal events carry no reason or historical Start date, so reasons come from the scope record and dates from the child's current project item. A removal event without a timestamp, or a timeline page that cannot be read, stops collection before publication. Because an unidentifiable removal cannot be matched to any child, it keeps the Feature's timing unavailable even if that child was later reattached. A child that left more than once is judged by its latest removal.

## Feature lead time

The agreed delivery measure uses Copenhagen calendar days from the earliest sub-issue Start date, including a discovery work item if it starts first, to completion of the last required work item. Discussion only on the parent does not supply a start, and Features do not contribute to work-item WIP or throughput. The Feature stays open until its business outcome is accepted and required work items are delivered. Removed scope and its reason are recorded without resetting the original start; not-planned closures are not delivered work, and missing dates stay unavailable. Reopened required work reopens completion and moves the finish to eventual completion; later enhancements after accepted completion are new scope. Wholly withdrawn Features have no completed Feature lead time and are shown separately. The Features table and published JSON now report this metric for available current direct-child evidence (#61); Feature durations remain separate from work-item charts.

A completed observation requires a nonempty Feature closed as completed after every required child was delivered as completed. Parent closure records human acceptance. Board status and the title alone never establish delivery or acceptance. A parent closed too early shows a linked data problem; a child closing later does not renew that acceptance. The parent must be reopened and closed as completed after delivery. An open parent whose required work is delivered says **Awaiting acceptance**, with continuing age and no completed lead time.

For example, discovery starts **16 November 2026**, the last required delivery is **20 November**, and parent acceptance is recorded **23 November**. Only after acceptance does the Feature report **4 days**, with 20 November as finish and no continuing age. Same-day completion is numeric zero and displays as **< 1 day**. The details show the acceptance timestamp separately from the finish date.

A required child reopening withholds completed timing and identifies any still-closed parent inconsistency. Child details mark reopened work. After delivery and renewed parent acceptance, the original earliest Start date remains in use and the finish becomes the latest required delivery. Missing reopen timestamps in older evidence prevent verification of renewed acceptance. Reopen timestamps use the same calendar validation as close timestamps; impossible dates cannot verify renewed acceptance. A reopened child remains started even if it returns to Ready or Backlog without project status history. Its missing or invalid original Start date makes Feature timing unavailable instead of selecting a later sibling date. Missing or invalid child Start or close dates identify the affected child and withhold timing; an available sibling never fills the gap.

The JSON adds `finishedAt` (Copenhagen delivery date), `acceptedAt` (verified parent closure timestamp), and `leadTimeDays` to each Feature observation, plus child `reopened` evidence. Unavailable or incomplete durations are `null`, never zero. `state` distinguishes Withdrawn, Completed, Awaiting acceptance, Reopened, Ongoing, Not started and Not available; linked `problems` explain evidence gaps. Completed Features have `ageDays: null` (displayed as Not applicable). A finish may be known while a missing start prevents lead time. Acceptance may be verified even when a missing start prevents timing.

**Controlled demo:** `cd apps/docs && npm run verify:flow-metrics` collects fixture responses, builds an isolated site, checks rendered/published agreement and saves desktop/narrow-screen screenshots under `apps/docs/test-results/flow-metrics/`. It covers retained recognition after a rename, work-item exclusion, the linked naming problem, accepted completion, later acceptance, premature closure, reopening, missing starts, same-day delivery, Copenhagen midnight across the autumn clock change, an archived completed Feature keeping its interval, an archived child and an off-board child whose lost Start dates are identified, and a child GitHub answers as not found. It covers a child moved from one Feature to another, an unlinked child, a reattached child, a removal whose child cannot be identified, and a Feature whose removal of its earliest work is on a second timeline page (#66). It also checks that this Feature evidence leaves every work-item value, WIP and throughput included, as it would be without it, and that a failed child read stops collection. Vitest also checks paginated title history, stable-identity deduplication across board and archived copies, that children already on the board are not read again while those of withdrawn Features are, unavailable or off-project children, paginated child project items and failures that stop collection, missing/invalid close dates and spring daylight-saving boundaries. Vitest covers membership history on a later timeline page, unlinked former children read outside the board or archived on it, work started after leaving and on the day it left, a child moved on again or unlinked after a move, and failing membership pages. No board is mutated; this work does not establish completion of Feature #42.

## Withdrawn Features

A Feature parent closed as not planned appears in the separate **Withdrawn Features** section, with linked children and its recorded reason. Record one `Withdrawal reason: <reason>` line in the parent issue body (an optional Markdown bullet is supported). Missing, empty, unsupported or multiple reason records produce a linked data problem; the report never invents a reason or edits an issue. Free-form comments are not interpreted as withdrawal records.

The published observation has `state: "Withdrawn"` and `withdrawalReason` (text, or `null` when missing or ambiguous). `acceptedAt`, `finishedAt`, `ageDays` and `leadTimeDays` are `null`: withdrawal is neither capability delivery nor ongoing work. The view displays age and completed lead time as Not applicable. The `timingState` field independently distinguishes Available, Not started and Not available start evidence for every Feature, including withdrawn ones. The view uses this field to explain an absent Start date without interpreting diagnostic messages. Child evidence and any unavailable dates remain visible even when the withdrawal reason is unavailable.

Delivered discovery and other delivered children keep their original work-item completion week and cycle time. Children closed as not planned remain closed without delivery and enter neither throughput nor cycle time. Withdrawal does not remove child scope or change the required-work denominator by itself. The controlled browser demo includes withdrawal after delivered discovery, alongside pipeline tests for missing and ambiguous reasons. Archived and off-board children of a withdrawn Feature are read as Feature evidence like any other (#65); the direct-child and historical membership limits still apply.

## WIP

Open work items with status **In Progress** or **Delivery Initiated**, each column against its own limit. Source: the status field of each issue on the board.

## Ready queue

Open work items with status **Ready**, waiting to be pulled, with their Priority and Size. It is not WIP. Source: the status field of each issue on the board.

## Cumulative Flow Diagram (CFD)

Daily counts in each board status, replayed from the issue timeline after duplicate Backlog additions have been removed (ADR-0002). Backward moves transfer an item between bands rather than adding work. Each point ends at Copenhagen midnight; today's point ends at collection. The latest point uses the board's current statuses. Closed items stay in their board status, including Done and items closed without delivery, so this chart describes board inventory rather than throughput. Missing status history is not backfilled: an item with no events first appears at collection time. Historical counts cover only items still on the board today.

## WIP limit breaches

Continuous periods when open work items exceed the current limit for In Progress, Delivery Initiated or the Ready queue. Close and reopen events stop and resume an item's contribution. The list shows column, limit, start, end (or ongoing), and peak excess. Breaches shorter than a day remain visible even when the daily chart misses them. Historical limits are unavailable, so today's limits apply to the whole history.

## Throughput

Work items closed as completed in each Monday-to-Sunday ISO week in Europe/Copenhagen time, broken down by work type. Issues closed as "not planned" do not count. Source: the close date and close reason of each issue on the board.

## Cycle time

Copenhagen calendar days from the project Start date to the latest close date for completed work items. A same-day item contributes zero to the weekly average and displays as “< 1 day”. Reopened items use their last close date. Items without a Start date are excluded from this metric.

## Elapsed time

Wall-clock time from the first move to In Progress on the Start date to the latest issue close, rounded to the nearest minute. It includes waiting time. GitHub records both moments; when a start event is missing, the value is shown as “Not available” rather than inferred from the date.

## Work item age

Copenhagen calendar days from Start date to the observation date for an open work item. Items without a Start date cannot have an age calculated.

## Old work item

An open item above five days old until ten completed items have usable start dates; after that, above the nearest-rank 85th percentile of completed cycle times. The page shows which limit applies.

## Blocked

Open work items carrying the `blocked` label, with blocked WIP first.

## Closed without delivery

Work items closed as not planned. They appear separately and enter neither throughput nor cycle time.

## Data problem

A missing, invalid or later-than-close Start date on started or completed work, a missing precise start time for elapsed time, a closed work item without a close reason, or an open work item without a status. Neither value is inferred; a completed item still enters throughput.
