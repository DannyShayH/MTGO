Discovery for [Feature #42](https://github.com/DannyShayH/MTGO/issues/42), carried out on [work item #57](https://github.com/DannyShayH/MTGO/issues/57). **Discovery agreed:** The team confirmed Q1–Q17 and the connected reporting views in Q18, then invoked `/to-spec` and confirmed the testing boundaries. The specification belongs on the existing Feature parent. This page records discovery, not implemented reporting; `/to-tickets` remains a separate team invocation.

## Source evidence

- `apps/docs/scripts/board-collector.ts` collects board issues, current Start dates, close reasons, status history and close/reopen events. It collects only a sub-issue count, not child identities or membership history.
- `apps/docs/scripts/flow-metrics.ts` selects work items solely by `subIssueCount === 0`, so an empty Feature currently enters work-item calculations. It has no Feature duration calculation.
- `apps/docs/scripts/collect-board.ts` replaces the collected dataset under `apps/docs/.cache/`; the current pipeline does not preserve successive datasets as a durable Feature history.
- `apps/docs/scripts/build-flow-metrics.ts` generates the shared reporting JSON and falls back to clearly marked sample data when no collected dataset is present. The docs UI currently has Overview, Work items and Definitions pages.
- `scripts/workon.sh` preserves an existing Start date, but creates a new one with the machine's `date +%F`, without explicitly selecting Copenhagen time.
- Live GitHub GraphQL queries during discovery confirmed that `Issue` exposes native `parent` and `subIssues` relationships. `SubIssueAddedEvent` and `SubIssueRemovedEvent` expose a timestamp, actor and child, while corresponding child-side events expose the parent. Feature #42's timeline contains the addition of #57. These event fields do not include a removal reason or a historical project Start date; availability of the full historical evidence still needs checking.
- The live schema also exposes previous and current titles on `RenamedTitleEvent`, `archivedStates` on project item collection and `includeArchived` on an issue's project items. A date field value exposes its current date and creation/update timestamps, not a sequence of previous date values. These are schema checks, not proof that all old or removed project evidence is recoverable.
- [ADR-0002](/MTGO/architecture/decisions/0002-status-history-from-issue-timeline/) deliberately uses GitHub timeline history instead of saving daily board snapshots. Q13 reconciles Q8 with that policy: reconstruct from retained source evidence, and report unavailable timing when it cannot be recovered.
- GitHub's live schema gives the project item query a default `archivedStates` value of `[NOT_ARCHIVED]`. The later specification must explicitly include archived Feature evidence instead of assuming the current query returns it.

The agreed [domain model](/MTGO/product/domain-model/) and [ADR-0007](/MTGO/architecture/decisions/0007-features-and-work-item-flow-measures/) remain authoritative. The [restaurant recipe review](/MTGO/architecture/restaurant-recipe-review/) was read; Feature #42 concerns the GitHub/docs metrics pipeline and does not require Medusa implementation changes.

## Agreed decisions

| Question                   | Decision                                                                                                                                                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Q1: Feature recognition    | Require the existing `Feature: ` title prefix, including before children exist. Use native sub-issue relationships for membership. Other structural parents remain excluded from work-item metrics without automatically becoming Features.                                                      |
| Q2: Required scope         | Every direct child is required, including discovery, unless the team explicitly removes it from scope and records why. Keep one level of work items under a Feature; blocking links express ordering rather than membership.                                                                     |
| Q3: Completion evidence    | Publish a completed Feature lead time only after the parent is closed as completed and every required child is delivered. Use the latest required child delivery as the finish, not the later parent acceptance date. Premature parent completion is a data problem.                             |
| Q4: Missing dates          | A started or delivered child without a usable Start date makes Feature lead time unavailable; do not substitute the earliest known sibling date. Identify the child causing the data problem. A Backlog or Ready child that has not started does not itself cause a missing-date problem.        |
| Q5: Reporting              | Add a Features page alongside the existing metrics pages. Show linked work items, progress, earliest start, finish and completed lead time. Show Feature age separately for unfinished Features, plus withdrawn Features and data problems. Begin with a table; additional charts can wait.      |
| Q6: Recording starts       | Include explicitly Copenhagen-based creation of new Start dates in Feature #42. Preserve existing dates and the rule that rerunning `gh workon` does not reset them. Flag questionable historical dates rather than silently rewriting them.                                                     |
| Q7: Removing scope         | Normally keep removed work linked, record its reason on the parent and close abandoned work as not planned. Show removed scope separately. Delivered work keeps its delivery history, and removing scope does not reset the original Feature start.                                              |
| Q8: Preserving history     | Preserve evidence of the original start and membership through child removal or movement. Missing earlier evidence makes the duration unavailable. Q13 clarifies that evidence is reconstructed from GitHub rather than retained in a new board-snapshot store.                                  |
| Q9: Renaming               | A previously recognized Feature that loses its title prefix remains a Feature with a naming data problem. The collector never edits the title automatically.                                                                                                                                     |
| Q10: Reopening             | A reopened required child invalidates completed Feature lead time and makes a still-closed parent a completion data problem. Humans resolve issue and board changes. Renewed acceptance uses the original start and latest required delivery.                                                    |
| Q11: Withdrawal            | A wholly abandoned capability closes as not planned, appears separately with its reason and has no completed Feature lead time. Delivered discovery and other delivered children retain their work-item throughput and cycle-time treatment.                                                     |
| Q12: Progress              | Display delivered required work items out of all required work items, including discovery, rather than a business-completion percentage. List removed work separately. Empty Features say "No work items yet" rather than 100% complete.                                                         |
| Q13: Source history        | Preserve ADR-0002: reconstruct from GitHub's retained membership/title events and preserved Start dates, including former children. No snapshot branch or automatic repository commits. Missing source evidence makes affected timing unavailable; the specification must verify reconstruction. |
| Q14: Board coverage        | Include archived Feature parents and retrieve their relevant children. Identify unavailable children or required data instead of silently omitting them. Retrieving a child for Feature evidence does not change work-item board-membership rules.                                               |
| Q15: Historical correction | Recalculate available work-item history to exclude previously counted Features. Explain the change in definitions and the next flow review; preserve written past observations and add relevant correction notes.                                                                                |
| Q16: Collection failures   | Authentication, transport and incomplete pagination failures stop publication rather than publishing partial or sample numbers as live. Identifiable missing facts in a successful collection are linked data problems for the affected Features.                                                |
| Q17: Late membership       | Use a child's actual Start date even when it predates attachment or creation of the Feature. Record moves as scope changes and preserve the former Feature's original start too. The work item is counted once in work-item metrics.                                                             |
| Q18: Connected views       | The team confirmed the four-view layout below as the final shared understanding: separate Feature delivery and work-item flow, connected through child work-item details and links back to the Feature.                                                                                          |

The identity, history and completion trade-offs are recorded in [ADR-0016](/MTGO/architecture/decisions/0016-feature-identity-and-completion-evidence/). The [glossary](/MTGO/architecture/glossary/) defines Feature age separately from Feature lead time.

## Agreed reporting structure

Separate the two levels in the metrics navigation: **Overview | Work items | Features | Definitions**.

- **Overview:** The team's work-item flow: WIP and Ready queue, weekly throughput, cycle-time trends, the cumulative flow diagram and issues needing attention. Link to the Features view.
- **Work items:** Evidence behind those flow measures: current columns, blocked and old work items, completed work by week, individual cycle times and data problems. A work item can link back to its Feature; standalone work remains valid.
- **Features:** A table of capabilities and their own delivery timing, with linked child work items. Use Feature age for ongoing work and Feature lead time only for accepted completion. Include start/finish dates and visible evidence gaps; show withdrawn Features separately.
- **Definitions:** The counting rules shared by all views.

Illustrative Feature table; these are example values, not live board observations:

| Feature      | State       | Required work delivered | Feature age    | Feature lead time |
| ------------ | ----------- | ----------------------- | -------------- | ----------------- |
| Capability A | Ongoing     | 2 of 4                  | 6 days         | Not completed     |
| Capability B | Completed   | 5 of 5                  | Not applicable | 7 days            |
| Capability C | Not started | No work items yet       | Not started    | Not completed     |

Selecting a Feature reveals its child work items with links, status, Start date and delivery date, plus work-item age or cycle time as applicable. Removed scope and data problems remain visible alongside that evidence. Start and finish dates belong in the real Feature table even though this compact sketch omits them for readability. Do not mix Feature durations into the work-item cycle-time average or count parent Features in throughput or WIP.

This structure clarifies Q5 and was confirmed in Q18; it is not a UI implementation. Exact layout, source queries, data representation and vertical slices must satisfy the agreed observable behavior when the Feature is implemented.

## Specification handoff

The team confirmed the shared understanding and requested `/to-spec` on the existing [Feature #42](https://github.com/DannyShayH/MTGO/issues/42). There are no parked business disagreements. Source limitations remain implementation risks: verify complete pagination, archived and former-child retrieval, reconstruction of identity/start evidence, a readable representation of scope-removal reasons and representative sample data. If source evidence is insufficient, preserve the agreed unavailable-data behavior rather than inventing dates or silently changing the rules.

The team confirmed these testing boundaries for the specification:

- Prefer deterministic GitHub-response fixtures through the existing collector and metrics calculator to verify observable reporting values. Existing Vitest tests already inject HTTP responses and the observation clock.
- Use focused built-page checks to verify the connected Features and Work items views, their visible values, navigation and evidence gaps. This is new Feature-view coverage, not a claim that a docs browser suite already exists.
- Check the work-start wrapper in isolation with a controlled clock/timezone and stubbed GitHub and Git commands, verifying Copenhagen Start dates and preservation of existing dates without touching a real board or starting a real issue branch.

The specification deepens the existing MoM Feature parent without a new Feature issue, triage labels or board movements. The team invokes `/to-tickets` separately for eventual vertical work-item sub-issues; none are created by discovery or specification. Delivering discovery #57 must leave #42 open until the whole capability is accepted and its required work is delivered.
