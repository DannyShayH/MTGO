MTOGO operators register Restaurants, authorize their staff and decide whether each Restaurant takes part in the platform. Restaurant staff decide when their Restaurant is open. This page holds the agreed journeys for both actors, the acceptance examples, and how the work follows and changes the Medusa recipe.

## Where each actor works

| Actor            | Where                                                  | Language                                                                                                                 |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| MTOGO operator   | Medusa Admin, a **Restaurants** page                   | English only in the MVP ([ADR-0018](/MTGO/architecture/decisions/0018-english-only-medusa-admin-for-operators/))         |
| Restaurant staff | The partner app (`apps/partner`), with its own sign-in | Danish and English ([ADR-0017](/MTGO/architecture/decisions/0017-partner-app-for-restaurant-staff-and-delivery-agents/)) |
| Customer         | No view in Feature #43                                 | Not applicable                                                                                                           |

Every Medusa Admin user is an MTOGO operator. Restaurant staff never get Admin access. They sign in with their own actor type, and each staff account belongs to one Restaurant. The API reports outcomes as codes, such as one code per missing activation requirement, and each UI turns the codes into text.

## When something is missing or fails

| Situation                                                | What the actor sees                                                                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Activation with requirements missing                     | Admin refuses and names each missing requirement, for example "Published menu missing".                                              |
| Same pickup address as another Restaurant                | A warning on Create; saving is still possible.                                                                                       |
| Postal code not in the Danish register                   | Admin only offers codes from the register; the API refuses others and adds nothing.                                                  |
| Removing the last postal code of an active Restaurant    | Refused, with the reason.                                                                                                            |
| Removing commercial terms of an active Restaurant        | Refused, with the reason.                                                                                                            |
| Revoking the last authorized staff member                | Allowed. Admin warns that nobody can open the Restaurant or accept Orders, and suggests deactivation.                                |
| Inviting an email that already has a login               | Admin asks for a different email.                                                                                                    |
| Expired, used or cancelled invite link                   | Partner app: "This invitation is no longer valid. Ask MTOGO for a new one." (Danish or English).                                     |
| Revoked staff member acts or signs in                    | The next request fails. Partner app: "Your access to [Restaurant name] has ended" (Danish or English), and the person is signed out. |
| Open/Closed while inactive                               | The switch is disabled with its reason.                                                                                              |
| Open/Closed toggle fails, for example after deactivation | The reason is shown with the real current state, not the position the switch was moved to.                                           |

## Acceptance examples

The examples use synthetic data. Restaurant "Pizzeria Nørrebro" has pickup address Nørrebrogade 1, 2200 København N, contact phone +45 12 34 56 78, contact email `kontakt@pizzeria.example`, and delivery area 2200 and 2100.

### Activation

A missing requirement refuses activation with its code. Staff count only after accepting their invitation and while not revoked. A published menu is at least one published dish linked to the Restaurant with Danish and English names; sold-out dishes count. Until Feature #44 delivers menu editing, a seed script creates the synthetic menu. ADR-0012 already prevents a dish from being published without Danish and English names, so the activation check counts published dishes. The example of a dish named only in Danish belongs to #44.

| Rule | Pickup address | Contacts | Authorized staff                | Commercial terms | Published menu           | Delivery area   | Result                            |
| ---- | -------------- | -------- | ------------------------------- | ---------------- | ------------------------ | --------------- | --------------------------------- |
| A1   | Yes            | Yes      | None, only a pending invitation | Yes              | Yes                      | Yes             | Refused: authorized staff missing |
| A2   | Yes            | Yes      | Yes, but every one revoked      | Yes              | Yes                      | Yes             | Refused: authorized staff missing |
| A3   | Yes            | Yes      | Yes                             | No               | Yes                      | Yes             | Refused: commercial terms missing |
| A4   | Yes            | Yes      | Yes                             | Yes              | No dishes                | Yes             | Refused: published menu missing   |
| A5   | Yes            | Yes      | Yes                             | Yes              | Only unpublished dishes  | Yes             | Refused: published menu missing   |
| A6   | Yes            | Yes      | Yes                             | Yes              | Yes                      | No postal codes | Refused: delivery area missing    |
| A7   | Yes            | Yes      | No                              | No               | No                       | No              | Refused, naming all four missing  |
| A8   | Yes            | Yes      | Yes                             | Yes              | Yes, every dish sold out | Yes             | Active and Closed                 |
| A9   | Yes            | Yes      | Yes                             | Yes              | Yes                      | Yes             | Active and Closed                 |

Pickup address and contacts are required when the Restaurant is created and cannot be emptied afterwards, so the server check covers them without an example of its own.

### Eligibility for a new Order

Feature #43 delivers this rule and the Receiving new Orders line. Feature #46 applies it at checkout, and Feature #47 shows that existing Orders stay actionable.

| Rule | Active? | Open? | Delivery area contains the destination? | Receiving new Orders                   |
| ---- | ------- | ----- | --------------------------------------- | -------------------------------------- |
| E1   | No      | -     | -                                       | No, because the Restaurant is inactive |
| E2   | Yes     | No    | -                                       | No, because the Restaurant is closed   |
| E3   | Yes     | Yes   | No (destination 8000)                   | No, for that destination               |
| E4   | Yes     | Yes   | Yes (destination 2200)                  | Yes                                    |

### Opening, participation and history

- An inactive Restaurant cannot be opened. Activation leaves it Closed.
- Deactivating an open Restaurant without a reason is refused. With a reason, it becomes Inactive and Closed, and reactivating leaves it Closed.
- Each activation, deactivation, opening and closing appears in History with time and actor, and deactivation also shows the reason. Billing the service fee by active days (ADR-0006) uses this history.

### Staff access

- An invitation accepted within 24 hours makes the person authorized staff of exactly one Restaurant.
- After Resend, the old link is refused and the new one works once.
- A revoked staff member's next request fails. They appear under Former staff, and History keeps their name on earlier openings and closings.
- Staff of one Restaurant cannot read or change another Restaurant, and cannot call any `/admin` route.

## How we use the recipe

We follow the [Restaurant-Delivery Marketplace recipe](https://docs.medusajs.com/resources/recipes/marketplace/examples/restaurant-delivery) (pinned example commit `aae7665`, Medusa 2.14.0), checked against the installed Medusa 2.22.4.

| Recipe                                                                              | MTOGO                                                                                    | Why                                                                                |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| A `restaurant` module with `Restaurant` and `RestaurantAdmin`, in a `MedusaService` | Followed, with `RestaurantStaff` as the glossary name                                    | Coding standard: one concept keeps one name                                        |
| A staff actor type with Medusa auth and `authenticate()`                            | Followed, as the `restaurant_staff` actor, through `@medusajs/js-sdk` in the partner app | Reuses Medusa auth                                                                 |
| Restaurant ↔ product link                                                           | Followed. It defines the published-menu check                                            | The domain model maps dishes to Medusa products. #44's grill may replace the check |
| Staff sign up themselves and attach to any `restaurant_id`                          | Replaced by operator invitations following Medusa's admin invite pattern                 | ADR-0008: operators manage staff access                                            |
| `POST /restaurants` without authentication                                          | `/admin/restaurants` for operators only                                                  | ADR-0008: operators create Restaurants                                             |
| Removing staff hard-deletes the row                                                 | Revocation keeps the record as former staff                                              | ADR-0008: revocation preserves history                                             |
| Routes at `/restaurants` and `/users`, with bodies parsed in the handler            | `/admin/*` and `/partner/*`, with body validation in middleware                          | Coding standard §4.4 and §7.1                                                      |
| `address` as one text field; `description`, `image_url`, `handle`                   | A structured pickup address. Description, image and handle are dropped from #43          | A postal code is needed; Customer presentation belongs to #44 and #46              |
| Only `is_open`                                                                      | Active/Inactive participation, a delivery area, commercial terms and history added       | ADR-0006 and ADR-0008                                                              |
| No Admin UI                                                                         | Our own Restaurants page in Medusa Admin, built with the Admin SDK and Medusa UI         | The operator journey above                                                         |

The installed `@medusajs/rbac` module could restrict Admin users, but it is licensed, which is why staff work in the partner app instead of Medusa Admin. Medusa Admin 2.22.4 has no Danish translation of its own screens, which is the background to ADR-0018.

## Agreed slicing

These work items are sub-issues of #43, created from the [specification](https://github.com/DannyShayH/MTGO/issues/43#issuecomment-6803106769). Each one carries its own UI and text, with Admin text in English and partner text in Danish and English.

| Slice                                                    | Behavior shown in the demo                                                                                                                                                                                                                 | Blocked by |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| [S1 / #71](https://github.com/DannyShayH/MTGO/issues/71) | Operator registers a Restaurant: list, Create with the same-address warning, Details; starts Inactive and Closed.                                                                                                                          | None       |
| [S2 / #72](https://github.com/DannyShayH/MTGO/issues/72) | Operator completes the setup: delivery area, commercial terms, and the readiness checklist with its six requirements.                                                                                                                      | S1         |
| [S3 / #73](https://github.com/DannyShayH/MTGO/issues/73) | Partner app walking skeleton: `apps/partner`, `packages/i18n`, `packages/ui`, the "apps import packages, never each other" rule; a seeded staff member signs in and out; Overview shell and Dansk/English switch; CI build and smoke test. | S1         |
| [S4 / #74](https://github.com/DannyShayH/MTGO/issues/74) | Operator invites Restaurant staff: Pending, Copy invite link, Resend, Cancel, existing-login warning.                                                                                                                                      | S1         |
| [S5 / #75](https://github.com/DannyShayH/MTGO/issues/75) | Invited staff accept and reach the Overview with the Restaurant details card and "Awaiting activation by MTOGO".                                                                                                                           | S3, S4     |
| [S6 / #76](https://github.com/DannyShayH/MTGO/issues/76) | Operator revokes staff access: effective on the next request, Former staff, last-staff warning.                                                                                                                                            | S5         |
| [S7 / #77](https://github.com/DannyShayH/MTGO/issues/77) | Operator activates a Restaurant: server check with one code per missing requirement, Restaurant ↔ product link, seeded synthetic menu, history.                                                                                            | S2, S4     |
| [S8 / #78](https://github.com/DannyShayH/MTGO/issues/78) | Operator deactivates and reactivates with a reason; the guards on the last postal code and the commercial terms; History section.                                                                                                          | S7         |
| [S9 / #79](https://github.com/DannyShayH/MTGO/issues/79) | Staff open and close their Restaurant; the Receiving new Orders line in both apps; the eligibility decision table for #46.                                                                                                                 | S5, S7     |

If S3 grows beyond effort M, the staff sign-in becomes its own slice right after it. The Feature-level blocker #44 → #43 was removed; #44's work items are blocked by S1 (#71) and S3 (#73) instead.

## Left for the specification

These are implementation questions only; no business rule is open.

- The exact `/admin` and `/partner` paths and the codes for missing requirements and refusals.
- How invitations and staff status are stored, following Medusa's invite token pattern.
- The seed data for the synthetic Restaurant, staff member and menu.
- Playwright coverage for the partner app in `verify:applications`.
